# Native sampler

This original, dependency-free Rust helper is an owned foreground child. It accepts the ASCII command `sample\n` on stdin, emits one version-1 JSON batch per command, and exits on stdin EOF. Unknown commands produce a versioned error; oversized input terminates the helper. It does not launch background work, collect environment variables, write user configuration or terminate sampled processes.

CPU, memory and process creation identities are decimal strings. macOS BSD birth seconds/microseconds become a microsecond creation key; Windows FILETIME creation values remain exact 100 ns ticks. CPU output is always nanoseconds, using macOS task Mach ticks divided by the host `hw.tbfrequency`, and Windows user+kernel FILETIME values multiplied by 100. Optional `uptimeMs` is a measured elapsed duration: Linux boot uptime minus start ticks, macOS UTC microseconds minus verified BSD birth, and Windows UTC converted to FILETIME units minus exact creation. Wide birth values remain untouched; only the small elapsed duration becomes a display number. Missing or future timing stays unavailable. Sampling wall time is a monotonic helper clock. Do not reuse a CPU baseline after restarting the helper. Memory is resident bytes on Unix and working-set bytes on Windows; aggregate shared pages can be counted more than once.

The macOS backend validates native structure lengths and checks birth identity before and after task reads. It requires `kern.bootsessionuuid` and `hw.tbfrequency`; denied queries return unavailable rather than approximating identities or time units. Windows holds validated process handles, validates snapshot creation time and parent creation ordering, and closes every handle. Boot identity uses the `NtQuerySystemInformation` boot environment GUID; this specific information class is a compatibility gate because Microsoft does not promise it as a stable Win32 surface. If it is unavailable, sampling reports unavailable. Full target-platform tests are required before publishing a supported combination.

Development commands:

```sh
cargo test --locked --offline --manifest-path native/sampler/Cargo.toml
cargo build --locked --offline --manifest-path native/sampler/Cargo.toml
HAT_REQUIRE_NATIVE=1 node --experimental-strip-types --test test/process-native.test.ts test/process-protocol.test.ts
node native/sampler/package.mjs
```

Packaging uses locked offline builds and writes `native/sampler/artifacts/<Node-platform>-<Node-arch>/hat-sampler` (with `.exe` on Windows) plus a version-1 `sha256.json` and the linked Rust toolchain’s actual standard-library copyright/license notices. Development packaging requires that toolchain’s `rust-docs` component; release runtime needs no toolchain. An optional Rust target argument builds another supported installed target. The release packager stages this folder under root `bin/`. Runtime loads that local artifact and verifies its content hash before executing it; explicit developer `helperPath` bypasses the packaged-manifest lookup. Linux production collection uses the TypeScript procfs backend, not this helper.

Local verification on 2026-10-06: macOS ARM64 Rust unit tests verify the real allowed own-process BSD/resource APIs, structure sizes, CPU unit conversion and wide JSON identities. Node tests verify EOF and foreground-parent-death termination. Full live host sampling is blocked by this workspace sandbox: the boot-identity sysctl returns EPERM. `HAT_REQUIRE_NATIVE=1` preserves that as a failing release gate; default local tests mark the unavailable OS scan explicitly skipped. Linux ARM64/x64 and macOS x64 compiler checks pass, but these are not execution tests. Installing a Windows target failed under the restricted toolchain/cache environment; the Windows FFI source passed a standalone metadata syntax/type check using the local 64-bit compiler, not a Windows build or runtime test.
